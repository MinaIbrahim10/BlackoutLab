FIELD GUIDE
Make failure reproducible.
A laboratory for the response, not a claim of production autonomy.
01 / THE SYSTEM
Real state, pretend commerce.
The lab writes actual checkout intents, fake payment captures, reservations and orders to SQLite. Local mode hosts three service objects; Docker Compose separates them into HTTP services.
02 / THE EXPERIMENT
Break a known boundary.
The scenario injects an authored fault and sends two checkouts. Every run has a unique namespace. Failures are deterministic and repeatable; these are not arbitrary production outages.
03 / THE TEAM
Compare three strategies.
Runbook executes a known reference plan without AI. Single-agent uses one generalist agent. Multi-agent shares evidence across commander, observer, investigator, recovery engineer and verifier. Both AI modes receive measured verification feedback for at most three recovery attempts. Calls are sequential to limit local memory pressure.
04 / THE VERDICT
Verify the books.
Recovery requires all six checks: intents committed, payments matching orders, one reservation per order, stock matching orders, ledger conservation and faults disabled. Model output cannot override this verdict.
Start local Gemma
ollama pull gemma4:e4b
python -m blackout serve
The web server uses the Ollama endpoint configured at startup. The browser never holds API credentials. If inference fails, the run remains unresolved unless its actual checks pass; no runbook is silently substituted.
Measure the difference
python -m blackout benchmark --mode runbook --trials 3 --output runbook.json
python -m blackout benchmark --mode single --trials 3 --output single.json
python -m blackout benchmark --mode multi --trials 3 --output multi.json
Compare the same machine, model, scenarios and trial counts. Small, authored fault cases do not establish that a multi-agent team is better in general.
